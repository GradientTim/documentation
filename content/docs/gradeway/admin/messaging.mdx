## Why

The messaging broker powers Gradeway's real-time features by syncing data changes across server and proxy instances.
For example, if Player A is connected to the lobby and an admin modifies Player A's data from a different server, Player A receives that update instantly, without needing a reconnect or manual refresh.

## Activate and Configure

Make sure that a messaging driver is located in the `drivers` folder and that it can be loaded successfully.

Set `messaging.enabled` to `true` in `config.toml`, and set the driver's ID in `messaging.driver`. The configuration file should now look like this:

```toml [config.toml]
[messaging]
  enabled = true
  # replace the driver id with the one you have installed and configured
  driver = "redis"
```

## Encryption

Some messaging drivers display a warning if neither encryption nor signing is enabled, as this
could result in payload data being readable by anyone who can observe the underlying transport
(e.g. another client subscribed to the same Redis/Postgres channel), or forged/tampered with
undetected. The encryption feature can be enabled for any messaging driver.

Encryption uses AES-GCM, so a payload encrypted this way is both confidential and authenticated:
Gradeway also rejects a payload that was tampered with or wasn't encrypted with the same key,
without needing anything else configured. Encryption is highly recommended if the warning appears
and Gradeway is being used in a production system.

If you want payloads to stay readable (for example while debugging with `LISTEN`/`NOTIFY`) but
still want tampered or forged payloads rejected, see [Signing](#signing) instead, it can be used
on its own or together with encryption.

### Generate a random secret [step]

```shell
openssl rand -base64 16
```

The command above will generate a random Base64 text that looks like this:
`YAYDeuwpdh6Y9toYDN+C2Q==`

### Configure the Environment [step]

```toml title="config.toml"
[messaging]
  # ...
  [messaging.variables]
    # ...
    GRADEWAY_ENCRYPTION_ENABLED = true
    GRADEWAY_ENCRYPTION_KEY = "PASTE_THE_SECRET_FROM_STEP_1"
```

<Callout type="warn">
  **This configuration must now be added wherever Gradeway is used; otherwise, the data for
  real-time updates will be skipped when the payloads cannot be successfully verified / decrypted.**
</Callout>

### Start the server / proxy [step]

After you start your server or proxy, messaging will work just as it did before, except that the
payloads will now be encrypted.

## Signing

Signing proves that a real-time update payload was produced by someone holding the shared signing
key, and that it wasn't altered in transit, without hiding the payload's contents. This is useful
when you want to reject forged or tampered payloads but don't need (or don't want) the payload
itself to be unreadable, for example while inspecting messages directly on the broker with
`LISTEN`/`NOTIFY` or a Redis client.

If you also need the payload's contents to stay confidential, see [Encryption](#encryption)
instead. Encryption already authenticates payloads on its own (it uses AES-GCM), so signing isn't
required for that. Signing and encryption are independent, you can enable either one on its own,
or both together for defense-in-depth.

### Generate a random secret [step]

```shell
openssl rand -base64 16
```

The command above will generate a random Base64 text that looks like this:
`YAYDeuwpdh6Y9toYDN+C2Q==`

### Configure the Environment [step]

```toml title="config.toml"
[messaging]
  # ...
  [messaging.variables]
    # ...
    GRADEWAY_SIGNING_ENABLED = true
    GRADEWAY_SIGNING_KEY = "PASTE_THE_SECRET_FROM_STEP_1"
```

<Callout type="warn">
  **This configuration must now be added wherever Gradeway is used; otherwise, the data for
  real-time updates will be skipped when the payloads cannot be successfully verified.**
</Callout>

### Start the server / proxy [step]

After you start your server or proxy, messaging will work just as it did before, except that the
payloads will now carry a signature that's verified on the receiving end.

## Signing and Encryption Together

If both are enabled, Gradeway encrypts a payload first and then signs the resulting ciphertext, so
a forged or tampered payload is rejected by the signature check alone, without ever attempting to
decrypt it. Both variables need their own key:

```toml title="config.toml"
[messaging]
  # ...
  [messaging.variables]
    # ...
    GRADEWAY_ENCRYPTION_ENABLED = true
    GRADEWAY_ENCRYPTION_KEY = "PASTE_A_SECRET_HERE"
    GRADEWAY_SIGNING_ENABLED = true
    GRADEWAY_SIGNING_KEY = "PASTE_A_DIFFERENT_SECRET_HERE"
```

<Callout type="idea">
  Since encryption already authenticates its payloads, combining it with signing is optional
  defense-in-depth rather than a requirement, most setups only need one or the other.
</Callout>
